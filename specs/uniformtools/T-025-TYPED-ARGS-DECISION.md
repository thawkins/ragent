# T-025 - Typed arguments for the canonical tool-call record (FR-001)

**Spec ID:** uniformtools
**Task:** T-025
**Requirement:** FR-001 (one canonical tool-call record)
**Status:** completed
**Dependencies:** T-001 (canonical types extended), T-012 (`decode_tool_arguments`)

FR-001 requires every tool invocation, from every provider, to be represented
as exactly one canonical record carrying a non-empty `id`, a `name`, and
**decoded JSON `input`**. Three places in `ragent-types` still carried a
`TODO: Replace Value with a typed struct` marker against that record:

| # | Site | Field |
|---|------|-------|
| 1 | `crates/ragent-types/src/message/mod.rs:100` | `ToolCallState::input` (`Value`) and `ToolCallState::output` (`Option<Value>`) |
| 2 | `crates/ragent-types/src/llm.rs:182` | `ContentPart::ToolUse::input` (`Value`) |
| 3 | `crates/ragent-types/src/llm.rs:210` | `ToolDefinition::parameters` (`Value`) |

This document is the recorded decision the task asks for: **all three stay
`serde_json::Value`, and each is now documented in place as a deliberate design
choice rather than as an open TODO.** The reasoning is below; the inline docs
at each site state the short form and point here.

## Decision

`serde_json::Value` is kept for every one of the three fields. No new type, no
new dependency, no change to any on-the-wire shape.

## Why a typed struct is the wrong answer here

### 1. The shape is owned by the callee, and the callee set is open at run time

A typed struct is only meaningful if the field's shape is fixed at compile time.
It is not. The value's layout is defined by whichever tool was called, and the
registry is not a closed set:

- the built-in registry alone registers 148 tools (README "Comprehensive tool
  system"), each with its own hand-written `parameters_schema()`, spread across
  `ragent-tools-core`, `ragent-tools-extended`, `ragent-tools-vcs` and
  `ragent-agent/src/tool`;
- on top of that, every MCP server the user connects registers its own tools
  (`crates/ragent-agent/src/mcp/mod.rs` converts `inputSchema` per server), and
  every enabled plugin registers the tools its manifest declares
  (`crates/ragent-plugins/src/tool_adapter.rs`);

so the harness first sees some tools' schemas mid-session, after the binary was
compiled. Any enum-with-one-variant-per-tool would have to be regenerated by a
build script from a set that is not fully known at build time, and would still
be wrong the moment a user connects a server.

This is the same reason `Tool::execute` itself takes `Value`: the tool trait is
the abstraction boundary, and the argument type on the far side of it is the
tool's business. A second typed layer on the history record would have to be
converted back to `Value` at exactly that boundary, adding a conversion without
adding a guarantee.

### 2. The provider wire layer must round-trip the payload unchanged

`ContentPart::ToolUse::input` and `ToolCallState::input` are both re-encoded to
the provider: tool history is replayed every step, and FR-006 / FR-018 require
that replay to be faithful. A typed struct with a fixed field set is lossy by
construction - any key a provider sent that the struct does not model is dropped
on the round-trip, so the model's next turn sees a different tool call than the
one it made. `Value` preserves the payload byte for byte. FR-001 explicitly
requires "no provider-specific field, key name, or envelope" to be lost on the
way into the persisted form; `Value` is the representation that delivers that.

### 3. `ToolDefinition::parameters` is third-party JSON Schema and cannot be a
   closed type without either loss or a new dependency

The parameters field is *forwarded*, not interpreted. Its owners are:

- in-tree tools, which hand-write `json!` schema literals, and
- MCP servers and plugins, which hand over arbitrary JSON Schema documents
  (`"$ref"`, `"oneOf"`/`"anyOf"`, `"if"`/`"then"`/`"else"`,
  `"patternProperties"`, vendor extensions, ...) that ragent does not control
  and cannot enumerate.

Measured over the in-tree schema literals actually in the tree
(`ragent-tools-core`, `-extended`, `-vcs` and `ragent-agent/src/tool`), the
keyword spread alone rules out a small closed struct:

```
additionalProperties 138   "items" 27    "format" 18   "default" 6
"enum"                46   "pattern" 9   "minimum" 5   "maximum" 1
"const" 2
```

and the third-party schemas ragent forwards are not limited to that set at all -
an MCP server may send `$ref`, `oneOf`/`anyOf`, `if`/`then`/`else`,
`patternProperties` or a vendor extension, and ragent has no way to enumerate
them ahead of time.

A typed subset would therefore have to do one of three things, and all three are
forbidden by this spec:

- **drop the keywords it does not model** - changes the bytes the model is told.
  FR-003 requires the encoder's cache hit to be byte-identical to a miss and
  forbids a provider from constructing its own tool array, so a typed subset that
  silently shed, say, `additionalProperties` (138 occurrences among the in-tree
  schema literals) would hand every provider a different tool contract than the
  one this repository declares;
- **be an opaque newtype around `Value`** - which is `Value` with extra steps
  and no additional guarantee, so it fails the "documented typed-argument
  decision" test: it would be documentation dressed as a type;
- **model full JSON Schema properly** - needs a schema crate
  (`schemars`/`jsonschema`), which NFR-002 forbids: "The change **shall** not add
  an external crate". `schemars` is in `Cargo.lock` only as a transitive
  dependency of `rmcp`, not as a ragent dependency, and `rmcp`'s own
  `InputSchema` is exactly the opaque-wrapper shape rejected above.

The harness's actual use of the value is deliberately tiny and already typed
where it matters: `validate_required_args` (`crates/ragent-tools-core/src/schema.rs`)
reads `required` and per-property `type` and enforces those two predicates
before execution; everything else is forwarded untouched, and the module header
states that stricter keywords are "intentionally not enforced".

### 4. The guarantees a typed struct would claim are already enforced

FR-001 asks for "decoded JSON `input`". That guarantee is real and it is
delivered - by behaviour, at the one place where it can be checked:

- `ragent_types::tool_args::decode_tool_arguments` (T-012, FR-007) is the single
  decode site. It returns `Value::Object` or an error; a non-object (array,
  number, `null`) never becomes a tool's input, and the caller turns the error
  into a corrective, model-visible message (FR-008) instead of executing;
- `validate_required_args` then checks the object against the callee's own
  schema before any guard, hook, permission check or backend call runs (FR-009,
  FR-014).

So the property "the input of an executed tool call is a JSON object satisfying
the callee's declared required/type constraints" holds today without a new type.
A struct would restate it statically for the in-tree tools and could not state it
at all for a bridged one - a strictly smaller guarantee than the runtime check
that already covers both.

### 5. `ToolCallState::output` is not even part of FR-001's contract

FR-001 constrains the tool-call *record* (`id`, `name`, decoded `input`). `output`
holds whatever the tool's `ToolOutput` carried; `ToolOutput.metadata` is itself
`Option<Value>` by design (`crates/ragent-tools-core/src/lib.rs`), so typing the
history field while the tool-side field stays `Value` would put the type
boundary in the wrong layer and force a conversion on every result. The harness
never interprets `output` - it hands it to the provider's result encoder - so
`Value` is exactly the right level of abstraction at that layer.

## What was done instead of a new type

1. **All three markers are gone.** Each is replaced by a `///` doc comment that
   records the decision, names the reason, and points at this document:
   - `ToolCallState::input` / `ToolCallState::output`
     (`crates/ragent-types/src/message/mod.rs`);
   - `ContentPart::ToolUse::input` (`crates/ragent-types/src/llm.rs`);
   - `ToolDefinition::parameters` (`crates/ragent-types/src/llm.rs`).
2. **A structural guard pins the decision**, so it cannot silently flip back to
   an undocumented TODO or to a lossy typed field:
   `crates/ragent-types/tests/test_typed_args_decision.rs`.
3. **The crate documentation records it** (`crates/ragent-types/DOCS.md`) and the
   `CHANGELOG.md` Unreleased section names the task.

## The guard (`tests/test_typed_args_decision.rs`)

The test is hermetic - it reads the crate's own `src/` tree from
`CARGO_MANIFEST_DIR`, needs no network and no build artefact - and asserts:

| Assertion | What it protects |
|---|---|
| `ToolCallState::input` is declared `Value` and `output` is `Option<Value>` | A future edit cannot silently narrow either field |
| `ContentPart::ToolUse::input` is declared `Value` | Same, for the wire-side record |
| `ToolDefinition::parameters` is declared `Value` | Same, for the forwarded schema |
| No `TODO: Replace \`Value\` with a typed` marker remains in `src/` | The marker cannot come back undocumented |
| Each of the three sites carries a doc comment naming the decision record | Documentation cannot be dropped from one site while others keep it |
| The decision record `specs/uniformtools/T-025-TYPED-ARGS-DECISION.md` exists and names all three sites | The referenced rationale stays resolvable |

The test does not assert on prose wording beyond those anchors, so the
explanations stay editable.

## Consequences

- **Nothing changes at any call site.** No signature, no serialised form, no
  storage schema. Persisted sessions written before this change replay verbatim
  (FR-028).
- **The `ragent-types` re-export surface is unchanged** - no new public item is
  introduced by this task.
- **A future change that does want a typed schema** must land as its own
  proposal: it needs a dependency decision against NFR-002 and a losslessness
  argument against FR-003/FR-018. This document is the written record that the
  current `Value` is a decision, not an oversight - which is exactly what the
  TODO asked for and could not itself express.
- **`crates/ragent-config`'s three sibling markers are out of scope.** The
  `TODO: Replace \`Value\` with typed ...` comments in
  `crates/ragent-config/src/{permission.rs,config.rs}` were not named by this
  task (it names `ragent-types`) and remain tracked separately
  (`ANTIPAT.md` M2.8, L-8).
