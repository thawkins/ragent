  Claude code hooks are not about telling the model what to do. They are about deciding when something must happen. In
  most setups, we write rules like “update the README after code changes” and hope the model follows them. As the
  diagram shows, that still leaves room for interpretation. Sometimes it works. Sometimes it quietly does not. Let’s
  break it down: 🔹 Think in lifecycle events → Every workflow is a sequence of moments: code changes, tool calls, task
  completion 🔹 Attach behaviour to those moments → Instead of a rule, define: “When code changes complete → update
  README” 🔹 Turn suggestions into guarantees → The model no longer decides; the action is triggered every time 🔹 Shift
  your mental model → Stop asking “will it remember?” and start asking “when should this always happen?” — 💬 Where in
  your current setup are you still relying on the model to remember something critical? 👇 Check out the full post and
  start thinking in events, not instructions (links in comments)

  Last week I made a tool that takes Claude Code from 70% to 96% task completion, while cutting costs by 17%. The
  problem: [Anthropic][124]'s Claude Code searches the repo in front of it well, but it can't search what already
  happened - the design decisions, the rejected alternatives, the partially completed work that only exist in earlier
  sessions. The default memory file is capped at 200 lines and pruned aggressively, so in practice prior project context
  didn't survive between sessions. Yare is a per-prompt retrieval layer delivered through Claude Code's hooks rather
  than as a tool the model has to call. The architecture indexes the real session conversations, runs dense retrieval
  plus a supersession graph for ranking superseded vs current claims, and renders a context block into every prompt
  before the model has to know anything is missing. Latest evaluation results from a 40-scenario benchmark designed
  around prior-session memory: - +26% on task completion vs baseline  - 17% lower cost per completed task - 18% faster
  wall time per completed task - 34% less repository search per completed task Full writeup with limitations and
  methodology in the comments! The goal is to make this open source, but I want to know people’s thoughts first! Anyone
  wanting to know more or even try out the tool, especially people working on agent memory, evals, or coding agents, hit
  me up!

  You hit your Claude Code limit by lunch. 8 habits that 3x every session: Claude Code counts tokens, not messages.
  Every file, folder, and system prompt eats your window. Here are the 8 habits that keep your sessions long: 5 key
  habits 1. /compact at 50% Run /compact at the halfway mark. Wait until 95% and you compact a degraded context. 2.
  /clear between tasks Old messages cost tokens Claude re-reads every turn. Finish a task, start a fresh session every
  time. 3. Read files, not folders A single file costs around 800 tokens. A folder tree costs around 12,000. 4. Plan
  before you build /plan is read-only and far cheaper than rebuilding. Failed builds cost more than ten minutess of
  planning. 5. /context to audit Run /context to see what is eating your window. System, MCP tools, memory, messages,
  all itemised. Match /effort to the task ✦ Low or medium for quick edits and boilerplate ✦ High for real coding and
  multi-step work ✦ Xhigh or max for hard architecture and bugs Opus strategises. Sonnet executes. 6. Write a
  [CLAUDE.md][132] Stack, rules, and tone in one file at your project root. Claude reads it every session automatically.
  7. Build skills Save your most-used prompts as skills. Loads them when needed instead of you re-pasting. 8. Use
  subagents Send heavy reads or research to a subagent. It returns a summary and your main thread stays clean. The
  advantage is not "using Claude Code more." It's using your tokens effectively. Get more free AI guides here →

  Opus 4.7 is more literal than before. My prompts didn't break loudly — they just started following instructions more
  exactly than I intended. That was the push I needed to actually study Anthropic's updated prompting guidelines. And
  here's the meta takeaway: build a prompt improvement skill. Run it on every important prompt you use — system prompts
  baked into your stack and prompts you run yourself. The model changed; your prompts should too. — My take, sharpened
  with Claude ✍️ ——— 🤖 3 takeaways I picked from this source — summary generated by Claude Code: ▸ More literal
  instruction following. "Format every section" and "format this section" are now different instructions. State scope
  explicitly — great for pipelines, but prompts that relied on implicit generalization need re-tuning. ▸ New effort
  levels xhigh and max — and effort depletes tokens faster. xhigh is the new default for coding/agentic work; max exists
  but risks overthinking. Higher effort burns tokens faster, so it's worth switching between medium, high,
  and xhigh depending on the task. Don't just port your 4.6 effort setting. ▸ Coverage-first code review. Opus 4.7 finds
  +11pp more bugs — but if your harness says "only report high severity," it now obeys that more literally and silently
  drops real bugs. Split finding from filtering: ask for full coverage first, rank in a second pass. ——— I share this to
  invite you on my knowledge journey. 👇 Full wiki summary in the first comment. Source: [https://lnkd.in/d3T-8FZB][141]

  I've been wanting to build Coeus since around 2014. I tried in React. Ruby on Rails. Even Clojure. Never got it right.
  The idea kept sitting there. Meanwhile I cycled through every note app I could find. Evernote, Notion, Obsidian,
  Logseq, Roam, probably 15 others. Same pattern every time: set up a system, use it for a few months, slowly stop
  because the organizing took more energy than the writing. I have ADHD. Didn't know that until my late 30s. It explains
  a lot about why "just be more disciplined about your system" was never going to work. Earlier this year I was deep in
  a project where I needed to track research and tasks. I'd gotten so frustrated with every app out there that I was
  writing things down on paper. And I'd been working with LLMs long enough by then to see what they could do with
  knowledge work. So I dusted off the idea and finally built the thing. Started with a simple web UI tied to a local LLM
  and a database. Then I switched to Markdown files so I could reference notes in other tools. Then it snowballed into
  what Coeus is now. It was never meant to be shared. I built it for myself because nothing else worked the way my brain
  works. But people kept seeing it, kept asking if they could use it, kept telling me to put it out there. So here it
  is. A desktop app that sits on top of your Markdown notes and connects them to AI. You write without thinking about
  structure. When you need something, you ask. It answers from what you actually wrote, not from a blank chat window.
  Your notes stay as plain files on your machine. You bring whatever AI you already use. I use it every day, even from
  my phone through Telegram when I'm away from my desk. It's a beta. I use it every day and it's getting consistent
  updates, but you will probably run into weird bugs or quirks. I'm not done with Coeus, far from it. If you try it I'd
  genuinely like to hear what works and what doesn't. That feedback is how it gets better. It's the thing I've been
  wanting to build for over a decade. Now I want to get it right. [https://usecoeus.com][157]
