GitLab Runner administration covers the full lifecycle of CI/CD job execution infrastructure in five steps: install GitLab Runner (available for Linux, Windows, macOS, and z/OS); register it using authentication tokens and set access scope as an instance, group, or project runner; choose an executor (e.g., shell on Windows or Docker on Linux) that determines where and how jobs run; configure the auto-generated `config.toml` for concurrency, logging, cache, CPU limits, and executor-specific settings; and continue scaling/optimizing. Tags—referenced in `.gitlab-ci.yml`—are the only way to route/filter jobs to suitable runners. Runners can execute jobs on the installed machine, in containers, in Kubernetes, or on cloud auto-scaled instances, with advanced features including autoscaling, performance optimization, fleet management, and Prometheus metrics for active jobs, CPU, memory, job success rates, and queue lengths.
