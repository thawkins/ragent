## Findings Not Applied (documented for future work)

### 2. `crates/ragent-specs/src/plan_parser.rs`

#### a. Default constructor for `PlanTask`

- **Lines:** 106–124
- **Problem:** The new `milestone` field and the existing 7-field struct are constructed repeatedly across tests and the parser itself (~20 call sites). Any future field addition will break every call site again.
- **Suggested fix:** Add a `Default` impl and/or a helper like `PlanTask::new(id, title, requirement, effort, priority)` that fills `dependencies`, `status`, and `milestone` with defaults. Update test literals and `parse_raw` to use the helper.

#### b. Redundant lowercase allocation in milestone matching

- **Lines:** 145–157 (`Milestone::normalise_item`), 547, 566–581 (`attach_milestones`)
- **Problem:** Every bullet line is converted to an owned `String` via `to_lowercase()` just so `attach_milestones` can compare it against the lowercased task title. This allocates once per milestone item per PLAN.md.
- **Suggested fix:** Change `normalise_item` to return a borrowed/cow helper, or compare case-insensitively with `eq_ignore_ascii_case`/`contains` on the already-normalised form. Keep storage in original casing unless the current lowercased storage is a deliberate normalisation contract.

#### c. Unicode-sensitive deliverable prefix slice

- **Lines:** 538–541
- **Problem:** The case-insensitive check is performed on `trimmed.to_lowercase()`, but the byte offset used to strip the prefix is taken from the original `trimmed`. For ASCII inputs this is fine, but if `to_lowercase()` ever changes byte length (e.g., Turkish "İ"), the slice will be wrong.
- **Suggested fix:** Strip the prefix from the lowered string or use a case-insensitive strip helper that returns the suffix after the matched prefix.

#### d. Duplicate checkbox-parsing logic

- **Lines:** 315–350 (`parse_gate_checkbox_line`)
- **Problem:** Logic for recognising `- [ ]`, `- [x]`, `- [X]` and stripping `**` markers overlaps with `Milestone::normalise_item`. Both manually index into the string and strip bold markers.
- **Suggested fix:** Extract a small helper that parses a markdown checkbox line into `(checked, body)` and a helper that strips surrounding `**`, then reuse it in both functions.

### 3. `crates/ragent-tools-core/src/apply_patch.rs`

#### a. Unnecessary `expect` on validated update content

- **Line:** 287
- **Problem:** `.expect("validated update must have content")` is reachable in practice if validation and write phases drift. It is not user-path safe and will panic instead of returning a tool error.
- **Suggested fix:** Replace with `let content = file_contents.get(&op.path).context("validated update missing content for {}", op.path.display())?;`.

#### b. Redundant line-count recomputation

- **Lines:** 164, 183, 196–197
- **Problem:** `content.lines().count()` is invoked multiple times on the same string; `.lines()` allocates an iterator and the count is not cached.
- **Suggested fix:** Cache `let lines = content.lines().count()` once per content snapshot and reuse it in the `OpResult`.

#### c. Overly complex `strip_prefix`

- **Lines:** 495–502
- **Problem:** The function allocates a `Vec<char>` and re-collects into a `String` to remove a single leading character.
- **Suggested fix:** Use `line.strip_prefix(prefix).map(|s| s.to_string()).ok_or_else(|| anyhow::bail!("Expected line to start with '{prefix}', got: {line}"))?`.

#### d. Dead-code hunk fields

- **Lines:** 336–346
- **Problem:** `Hunk::header` and `Hunk::end_of_file` are kept with `#[allow(dead_code)]` for "future diff-format round-tripping" but are not used today.
- **Suggested fix:** Either start using them (e.g., emit the header when rendering a diff preview) or remove the fields and the `allow` annotations. If they are genuinely needed for an upcoming feature, add a code comment with the tracking issue/spec ID.

### 4. `crates/ragent-agent/src/tool/list_agents.rs`

#### a. Status enum string mapping duplicated

- **Lines:** 96–103, 225–233
- **Problem:** The same `TaskStatus → &str` and `TaskStatus → emoji` mappings are written twice in the same file. The enum itself already implements `Display` (`task/mod.rs:104`), but this file uses a hand-written string switch.
- **Suggested fix:** Add a `TaskStatus::as_str(&self) -> &'static str` method on `TaskStatus` and a single `status_emoji` helper, then use them everywhere. This also keeps `list_agents` consistent with `processor.rs:1699` and other call sites.

#### b. `unwrap_or(Value::Null)` on serialisation

- **Line:** 76
- **Problem:** `serde_json::to_value(&entry.status).unwrap_or(Value::Null)` is unnecessary; `TaskStatus` already implements `Serialize` via the derive on the enum, and `to_value` cannot fail for a simple enum.
- **Suggested fix:** Replace with `json!(entry.status)` or keep `to_value(...)?` if an error is theoretically possible.

### 5. `crates/ragent-agent/src/tool/team_task_complete.rs`

#### a. Manual status string mapping

- **Lines:** 88–93
- **Problem:** `crate::team::TaskStatus` is matched to hard-coded strings in a debug-only block, duplicating the mapping that likely exists elsewhere.
- **Suggested fix:** Add `TaskStatus::as_str(&self) -> &'static str` to `ragent-team` or `ragent-agent::team` and reuse it.

### 6. `crates/ragent-agent/src/tool/wait_agents.rs`

#### a. Wait-loop subscription logic duplicated with `team_wait.rs`

- **Lines:** 86–147
- **Problem:** The pattern "subscribe to event bus, read current state, collect already-completed items, increment waiter count for running items, then wait for events" is very similar to `team_wait.rs`.
- **Suggested fix:** Extract a generic `wait_for_items` helper in `ragent-agent/src/tool/` or a shared module that takes an initial set of IDs, an event-filter closure, and a timeout. Both tools can then call it.

### 7. General cross-cutting notes

- Several tools use `anyhow::anyhow!("Missing required parameter: ...")` inline. A tiny helper `require_str(input: &Value, key: &str) -> Result<&str>` would remove ~15 lines of repetition across `cancel_agent.rs`, `new_agent.rs`, `team_spawn.rs`, `team_task_complete.rs`, etc.
- `format!("...")` durations in `list_agents.rs` and `format_task_detail` compute `chrono::Utc::now() - task.created_at` on every iteration for running tasks; for a large task list this is harmless but could be computed once before the loop.
